# stellar-dominion：品質を維持する軽量化案

対象：`tkjjjjjjjkjjj/stellar-dominion` の `main`、コミット `ba6627261a98ed76ac820bf49abcd815c14346af`。
ソース調査とローカルでの容量計測に基づく提案。今回のドラフトでは案1・2と、案3のうち不透明画面の裏側の休止を先行実装する。実機のCPU・GPU・消費電力は未計測のため、改善率は確定していない。

## 推奨方針

ゲームの進行速度、操作反応、SVGの細部、発光、編隊、音、戦闘演出を維持し、同じ値の再計算と見えていない処理を減らす。
最初は生産速度とUIの派生値のキャッシュを実装し、描画負荷の変更は実機の計測結果を見て追加する。

## 現状

- DOMの差分更新、アクティブなタブのみのUI更新、SVGのグラデーション定義の共有、パーティクルの待機時停止は実装済み。
- 非表示タブは `display:none`。これを新しい最適化として数えない。
- パーティクルは最大420個、CanvasのDPRは最大2。これらをさらに下げる案は初手に含めない。
- フォントはWOFF2、日本語はサブセット済み。音はWebAudio合成で音声ファイルの転送がない。

| 対象 | 容量 |
| --- | ---: |
| 起動用HTML・CSS・JS 7ファイル | 189,249 bytes（約185KiB） |
| 上記を個別にgzip level 9で圧縮した参考値の合計 | 50,854 bytes（約50KiB） |

gzip値はローカルでの参考計測であり、配信時の実転送量ではない。SWの合計は `./` と `./index.html` の両エントリーを含む。アイコン等の容量を通常の起動時転送量として扱わない。

## 1. 生産速度を変更時だけ計算する【最優先】

根拠：[`app.js:1025`](https://github.com/tkjjjjjjjkjjj/stellar-dominion/blob/ba6627261a98ed76ac820bf49abcd815c14346af/js/app.js#L1025) の毎フレームの `tick()` が、[`game-core.js:253`](https://github.com/tkjjjjjjjkjjj/stellar-dominion/blob/ba6627261a98ed76ac820bf49abcd815c14346af/js/game-core.js#L253) で `productionPerSecond()` を呼び、施設・征服補正等を計算し直している。

- UI側で生産速度のキャッシュを持ち、生産速度に関係する変更で無効化する。
- 対象は全施設レベル、征服状況、覇王星。ロード・リセット・超越によるstateの置換でも無効化する。
- 実績の覇王星獲得も対象にする。勝利時の征服ボーナスや強化後の生産を次のフレームから反映する。
- `tick()` に計算済み速度を渡せる形を検討する。通常の呼び出しでは従来どおり計算し、既存テストやオフライン計算との互換性を保つ。
- 資源加算、累計生産、時間制限は既存の処理を使う。毎フレームのHUD補間と操作時の即時更新は維持する。

期待：60/120Hz画面で毎秒約60/120回発生する生産速度の計算を、関連する状態変更時へ集約できる。これは計算回数の削減であり、ゲーム全体のCPU削減率ではない。

## 2. 詳細画面・戦力・コストを変更時だけ更新する【最優先】

根拠：[`app.js:262`](https://github.com/tkjjjjjjjkjjj/stellar-dominion/blob/ba6627261a98ed76ac820bf49abcd815c14346af/js/app.js#L262) の `facilityEffect()` と `updateDetail()` は、定期更新のたびに `structuredClone(state)` を作って次の強化・建造を試算する。DOMへの書き込みを省略していても、コピーとHTML生成は繰り返す。

- 「静的な試算」と「変化する資源表示」を分ける。
- 施設効果、次回解禁、艦隊戦力、コストは関係する状態が変わったときだけ再計算する。
- 定期更新は所持資源、不足表示、購入可否、残り時間、任務進捗を中心にする。タップや長押し成功時は即時更新する。
- 次のレベル・隻数を試すためのコピーは、`buildings` または `units` の小さなコピーで済ませる。state全体はコピーしない。
- HUD、戦闘カード、通知バッジで使う共通の戦力・勝率は再利用する。
- 戦闘プレビューの無効化条件は艦隊数、司令中枢、自動造船所、覇王星、連勝数、対象星域、超越回数。資源の増加だけでは再計算しない。
- 表示が変わらないstyle・属性の書き込みも抑える。

注意：単一のキャッシュですべてをまとめると無効化漏れが起こりやすい。生産・戦力・選択中の詳細など、依存関係ごとに管理する。

## 3. 画面を覆う演出の裏側を休止する【一部実装済み】

根拠：[`app.js:1088`](https://github.com/tkjjjjjjjkjjj/stellar-dominion/blob/ba6627261a98ed76ac820bf49abcd815c14346af/js/app.js#L1088) のプロローグ表示前に基地UIを構築している。戦闘中もベースの定期更新は続く。背景・施設にはCSSの常時アニメーションがある。

- 【実装済み】不透明なプロローグ／戦闘画面で完全に隠れる基地のCSSアニメーションを `animation-play-state:paused` で休止する。戦闘画面は背景のフェードイン完了後に休止し、閉じ始めた時点で再開する。
- 【実装済み】完全に隠れる画面のUI更新とHUD補間を保留し、閉じる時に一度同期する。HUDは隠れている間に収束していたはずの値をそのまま表示する。ゲームの生産計算は継続する。
- 半透明のヘルプやモーダルでは見えているアニメーションを維持する。
- `visibilitychange` でゲームループとFXを明示的に止め、復帰時は既存の最大8時間のオフライン計算で進行を回収する。
- 復帰時は `lastFrame` 等を更新し、隠れていた時間を通常tickとオフライン計算で二重加算しない。短い非表示時間も一貫した方法で扱う。
- 途中の資源フライ演出を終了・破棄する場合も、`onArrive` 相当の精算を必ず行い、HUDの `hold` を残さない。

期待：表示中の品質を保って、覆われた画面と非表示時の処理を減らす。非表示タブをすでに描画しない効果は含めない。

## 4. 読み書きのまとめ方とSVG生成を改善する【計測後】

根拠：[`fx.js:79`](https://github.com/tkjjjjjjjkjjj/stellar-dominion/blob/ba6627261a98ed76ac820bf49abcd815c14346af/js/fx.js#L79) の資源フライは、資源ごとの座標取得とDOM追加が交互に行われる。

- 先に出発点・到着点の座標をすべて読み、トークンをまとめて追加してからアニメーションを開始する。
- 施設アートは種類・Tier・ロック状態、艦船は種類・敵味方・クラス、惑星は種類・クラスをキーに生成結果を再利用する。
- アート文字列のキャッシュは生成負荷に効くが、SVGノード数やGPU描画の削減とは別。
- DOMノード数が実測で問題なら、繰り返し艦船の `<symbol>/<use>` を小範囲で試す。WebKitでのグラデーション、内部CSS、炎・盾・編隊の動きを検証する。
- Canvasの描画領域や粒子配列の再利用は、FXが実際のボトルネックだった場合に限って着手する。

この段階では全施設の画像化やアニメーションの削除は必要ない。

## 5. 配信用ファイルを圧縮・版管理する【読み込み改善】

根拠：[`pages.yml`](https://github.com/tkjjjjjjjkjjj/stellar-dominion/blob/ba6627261a98ed76ac820bf49abcd815c14346af/.github/workflows/pages.yml) はリポジトリ全体を配信しており、[`sw.js`](https://github.com/tkjjjjjjjkjjj/stellar-dominion/blob/ba6627261a98ed76ac820bf49abcd815c14346af/sw.js) は同一オリジンのGETをnetwork-firstで取得する。

- GitHub ActionsでJS/CSSのminifyとハッシュ付きファイル名を生成し、配信用ディレクトリを作る。元のソースは読みやすい状態を保つ。
- モジュールのリクエスト数が起動の遅延要因なら、JSをまとめる。実機で起動時間と圧縮後サイズを比較する。
- HTMLとSWの更新確認は維持し、版が確定したハッシュ付きアセットはキャッシュを利用する。
- 新しい一式の保存完了後に新バージョンへ切り替え、HTML・JS・CSSが別の版で混ざらないようにする。
- コード・必要フォントのオフライン起動を維持する。512pxのアイコン等を導入の待ち時間から外すかは、ホーム画面追加とオフライン動作を確認して判断する。
- PNGの可逆最適化は候補。フォントの削除や非可逆な画質低下は採用しない。

期待：コードの転送量と再訪時の待ち時間を改善する。minify後の削減率や配信サーバーの圧縮効果は、実際の配信を計測するまで確定しない。オフライン品質と更新の確実性が変わるため、CPU側の変更とは別の変更として検証する。

## 実施順と合格条件

1. 代表的なiPhoneとAndroidで現状を記録する。基地待機、Tier III＋最大表示編隊、建造長押し、戦闘、画面復帰、初回／再訪／オフライン起動を対象にする。
2. 案1・2を実装し、生産速度計算・状態コピーの回数、JS処理時間、メモリ割当、長押し時の遅延を比較する。
3. 必要なら案3・4を追加し、描画時間とフレーム落ちを測る。
4. 案5を独立して実装し、実転送量と起動時間、新版への更新、オフライン起動を確認する。

合格条件：

- 同じ状態・操作・経過時間・乱数で、生産、支払い、勝率、任務、超越の結果が一致する。積算の浮動小数点誤差だけは許容幅を明示する。
- 強化・建造・実績による覇王星獲得・征服・超越・ロード直後に、キャッシュした数値がすぐ更新される。
- 長押し、タブ切替、演出スキップ、短時間／長時間の離脱復帰で取りこぼし・二重加算がない。
- 通常演出でアート・発光・編隊・戦闘・資源フライを比較し、見た目と速度を維持する。星背景などの乱数は比較時だけ固定する。
- `npm test` と既存の構文チェックを通す。これらはゲームロジックの確認であり、見た目・操作・SWの確認を代替しない。
- 対象端末の画面更新周期に合わせてフレーム落ちを比較する。60Hzなら16.7ms、120Hzなら8.3msを基準にし、全体を30fpsに落とす方法で達成しない。

最初の変更範囲は案1・2。ここで改善が十分なら、描画方式を大きく変える必要はない。

## 先行実装の検証結果

ドラフトは案1・2を実装し、依存値を比較する `js/view-cache.js` を追加した。毎フレームの資源加算、HUD補間、通常の演出は維持する。Service Workerの事前キャッシュにも新モジュールを追加し、キャッシュ版をv11へ更新する。

- 既存20件と追加5件、合計25件のテストが成功。追加テストは全施設・兵種、同じ配列内の征服ID変更、覇王星、連勝、超越、ロードによるstate置換の更新と、従来tickとの一致を確認する。
- Chromium、390×844、DPR 2で変更前のコミットと比較。時刻・乱数・RAFを固定し、アニメーションを同じ時点に合わせた7画面（初期、待機後、採掘施設選択、強化後、艦船選択、征服、任務）の画像がピクセル単位で一致した。
- キャッシュが温まった後の600フレーム（60Hzで10秒相当）を固定状態で比較した処理回数は以下のとおり。テスト時だけコア関数の呼び出しを数えた。
- 案3の先行分：プロローグ表示中に裏で動く基地・背景のアニメーションが47→0、敗北結果画面の裏で動く征服画面のアニメーションが13→0、結果画面表示中3秒間の `#app` へのDOM書き込みが18→0。アニメーション時点を固定した比較で、プロローグ・戦闘結果・帰還後の3画面が変更前とピクセル単位で一致。勝利時の報酬フライ前後のHUD表示も変更前と一致した。
- 実際のタイマー・入力とService Workerを使い、長押し建造、6星域の戦闘スキップと報酬受取、超越、v11への新モジュールの事前キャッシュ、オフライン再読み込み後のセーブ復元をChromiumで確認した。ブラウザのJavaScriptエラーはなかった。
